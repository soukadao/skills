## 共通仕様

- `drawio` の `open_drawio_xml` toolを使用する
- 図を作成する前に、利用サービス、データフロー、外部アクター、クラウド境界を会話や文脈から把握する。不明点が図の正確性に大きく影響する場合だけ確認する
- 図を作成する前に、ネットワーク構成図、アプリケーション構成図、ワークフロー構成図のどれを主目的にするかを判定し、その図種別に合う配置ルールを優先する
- 生成するXMLは未圧縮の `mxGraphModel` とし、必要に応じてタイトル、短い説明、凡例を含める
- タイトルを置く場合は左上に配置し、図の主領域・グループ・線と重ならないようにする
- ページサイズは要素数に合わせて調整する。目安は小規模（3-5サービス）で `800 x 600`、中規模（6-12サービス）で `1169 x 827`、大規模（13サービス以上）で `1600 x 1200` 以上とし、凡例や注釈の領域を追加で確保する
- `mxGraphModel` には原則として `adaptiveColors="auto"` を設定し、明示色を使う場合もダークモードで判読できるコントラストを保つ
- 凡例は`assets/legend.xml`を参考し、他の図形と被らないように左下に配置する
- 線のテキストは背景色を**none**にする
- 図形の余白は**30px**以上取る
- 図形同士、図形とグループ境界、図形と線の間には最低 `30px` の余白を確保する
- 図形のラベルも図形領域の一部として扱い、ラベルが他の図形・線・グループ境界と重ならないようにする
- 線はサービスアイコン、ラベル、グループタイトルの上を通さない
- 線がサービスアイコンやラベルの上を通りそうな場合は、図形の配置を変えるか、余白のある外周側を通す
- 図形は検索をしてスタイルを取得しサイズの調整と図形の配置を行う
- 矢印や線は `common` カタログのコネクタ定義を使用し、手書きで `edgeStyle` を組み立てない
- 直角の矢印は `common/orthogonal-arrow`、直角の破線矢印は `common/orthogonal-dashed-arrow` を使用する
- 直角の矢印では `rounded=0` を維持する。`rounded=1` は角が丸く見えるため使用しない
- 線上のテキストは原則として使用しない
- 通信種別や用途は、線の色・線種と凡例で表現する
- 線の色・種類は凡例に定義されたものに沿って配置し、凡例にない色や線種を使わない
- `HTTPS`、`HTTP`、`DNS`、`SQL` など一般的なプロトコル名だけの線ラベルは省略する
- APIメソッド名、イベント名、処理ステップ名など、凡例だけでは意味が伝わらない重要な差分は近接注釈またはステップ番号で表す
- 手順や時系列が重要な図ではステップ番号を使ってよい。番号バッジは矢印の始点近くに置き、アイコンや線から最低 `10px` 離す
- 絵文字は図形ラベル、タイトル、注釈、凡例に使用しない
- すべての座標とサイズは可能な限り10px単位に揃える

## 出力と検証の流れ

1. 要件から図種別、主要サービス、外部アクター、境界、主通信経路を整理する
2. `scripts/shape-catalog.ts` で必要なプロバイダーサービス、グループ、外部アクター、共通図形、線のstyleを取得する
3. タイトル、クラウド境界、外部要素、主要サービス、補助サービス、凡例の順に配置する
4. 主通信経路を先に引き、監視・ログ・管理・CI/CDなどの補助線は外周寄りに逃がす
5. プロバイダー別の検証手順がある場合はそれを実行し、失敗したら配置・サイズ・線の経路を直して再検証する

## レイアウト標準

- 外部アクター（Users、GitHub、オンプレミス、SaaSなど）はクラウド境界の外に置き、クラウドサービスは原則としてクラウド境界内に収める
- 外部アクターは左側または上側、クラウド境界は主領域、凡例は左下または主領域の外側に配置する
- 主通信経路は左から右、または上から下に単調に進むように配置する
- 主要サービスは図の中央帯に置き、監視・ログ・セキュリティ・管理・CI/CDなどの補助サービスは上端、下端、右外周などに寄せる
- サービスアイコンへ線を接続する場合は、カテゴリ用の囲みやコンテナではなく、実際のサービスアイコンをsource/targetにする
- サービス名はサービスアイコン側のラベルに置き、カテゴリや論理グループの名前と混同しない
- 同じ種類の複数接続は、可能な範囲で代表サービス、実在する集約サービス、または集約線にまとめて線数を減らす
- 図が複雑になる場合は、線の追加よりもサービスの位置、グループサイズ、主経路と補助経路の分離を優先して整理する

## 線の交差回避ルール

- 主通信経路を最優先し、左から右または上から下へ一方向に流れるように配置する
- 主通信経路の線は、監視・ログ・管理系の線より短く、直線的に見えるようにする
- 線が交差しそうな場合は、以下の優先順で回避する
  1. 図形の配置を調整して、主通信経路を一直線に近づける
  2. 監視・ログ・管理系サービスを図の外周寄りに移動する
  3. 監視・ログ・管理系の線を破線にし、主通信経路との視覚的な優先度を下げる
  4. 同種の線をまとめられる場合は、既存のサービスアイコン、代表サービスノード、または集約線にまとめる
  5. どうしても交差する場合は、主通信経路ではなく補助線側が交差するようにする
- 線と図形の重なりは線同士の交差より優先して避ける。線がサービスアイコンやラベルを横切る配置は不可とする
- 監視・ログ・管理系サービスへの線は、複数の送信元から直接引かず、既存のサービスアイコン、代表サービスノード、または集約線にまとめてから接続する
- 監視・ログ・管理系の集約を表すために、吹き出し、注釈、ラベルだけの中継図形、雲形、付箋風の図形を追加しない
- 監視・ログ・管理系サービスは主通信経路の上端または下端に配置し、主通信経路と線が重ならないようにする
- 線の折れ曲がりは少なくし、不要なウェイポイントは追加しない
- draw.ioの自動ルーティングに任せるため、edgeには原則として手動のpointsを設定しない
- 線ラベルは、凡例だけでは意味が伝わらない重要な通信差分がある場合に限る
- 線ラベルを使う場合も、線上ではなく近接する注釈テキストとして配置し、線や図形と重ならないようにする

## 図形検索

図形の draw.io `style` は、`scripts/shape-catalog.ts` で検索して使用する。
直接 style 文字列を新規作成するのは、カタログに該当図形が存在しない場合に限る。

利用可能な図形一覧を確認する:

```bash
tsx scripts/shape-catalog.ts list
tsx scripts/shape-catalog.ts list common
```

特定の図形の style を取得する:

```bash
tsx scripts/shape-catalog.ts style common right-arrow
tsx scripts/shape-catalog.ts style common orthogonal-arrow
```

矢印、線、汎用矩形、テキスト、DBシリンダーなどプロバイダー非依存の図形は `common` カタログを使用する。

## 図の検証

プロバイダー別の検証スクリプトや検証ルールがある場合は、該当する `references/<provider>/specification.md` に従って客観的なレイアウト検証を行う。

検証対象:

- サービスアイコン同士が重なっていないこと
- サービスアイコンがグループの枠線に重なっていないこと
- サービスアイコンがラベル込みでクラウド境界内に収まっていること
- 線がサービスアイコンやラベル領域の上を通っていないこと
- 矢印や線同士が同じ経路上で重なっていないこと

検証スクリプトは未圧縮のdraw.io XML（`mxGraphModel`）を入力にする。圧縮済みURLや画像は検証対象にしない。
