# データベースモデリング

## 前提

- Entity は必ず `Resource` または `Event` に分類する。
- `Resource` は、業務上継続して認知される「もの」。
- `Event` は、ある時点で発生し、業務上の事実として記録される「こと」。
- Resource 同士を安易に直接結ばず、業務事実を表す Event を介して関係を表現する。
- 多値属性、繰り返し項目、明細、履歴は縦持ちにする。
- リレーションは「なんとなく関係がある」ではなく、業務上たどる必要があるアクセスパスとして置く。
- モデルが論理的に正しいだけでなく、現実の事業事実と一致しているかを検証する。
- 業務で認知されていない便宜的なIDや区分を、分析段階で勝手に作らない。
- データベース設計: 実装可能で論理的に矛盾しない構造を作る。
- データモデリング: 現実の事業構造と一対一に対応するモデルを作る。
- `L-真`: `Logic` に照らして真。形式・文法として無矛盾であること。
- `F-真`: `Fact` に照らして真。現実の事業事実と一致していること。
- `L-真` のモデルは複数あり得る。`F-真` のモデルを選ぶ。

## モデリング手順

### 1. 情報源を集める

- 帳票
- 画面
- CSV/Excel
- API仕様
- 現行DB
- ヒアリングメモ
- 業務フロー
- 規約、契約、申込書、伝票

- 情報源ごとに項目を列挙する。
- 最初からテーブル設計に寄せすぎない。

### 2. Identifier を探す

- 顧客番号
- 商品コード
- 注文番号
- 請求番号
- 契約番号
- 社員番号
- 店舗コード

- Identifier は単一項目とは限らない。
- 複合キーで業務上の単位を表している場合もある。
- 注文番号 + 行番号
- 契約番号 + 版数
- 店舗コード + 営業日
- 商品コード + 適用開始日

- Identifier から「番号」「コード」「ID」「No.」などを取り除いた名前を Entity 候補にする。
- 顧客番号 -> 顧客
- 商品コード -> 商品
- 注文番号 -> 注文
- 注文番号 + 行番号 -> 注文明細

### 3. Entity を Resource / Event に分類する

`Event` の判定基準:

- タイムスタンプ、発生日、処理日、適用日などを持つ。
- 監査証跡として残すべき業務事実である。
- 数量、金額、単価、残高、状態変化などの実績値を持つ。
- 「いつ起こったか」を問える。
- 「受注する」「出荷する」「入金する」のように動詞化して意味が通る。

`Resource` の判定基準:

- Event 以外の Entity。
- 業務上、継続して存在・参照される対象である。
- マスタ、台帳、一覧として管理されやすい。

| Entity | 分類 | 理由 |
| --- | --- | --- |
| 顧客 | Resource | 継続して認知される取引相手 |
| 商品 | Resource | 継続して販売・管理される対象 |
| 注文 | Event | 注文日、数量、金額を持つ業務事実 |
| 注文明細 | Event | 注文内の商品別の数量・単価を持つ業務事実 |
| 入金 | Event | 入金日、入金額を持つ業務事実 |
| 社員 | Resource | 継続して認知される人員 |

### 4. Resource と Event の関与関係を書く

```text
顧客(Resource) -- 注文(Event)
商品(Resource) -- 注文明細(Event)
注文(Event) -- 注文明細(Event)
```

- Resource 同士を直接結ばず、Event への関与として表現する。

### 5. 関係を4パターンで整理する

#### Resource - Event

```text
顧客 -- 注文
社員 -- 承認
店舗 -- 売上
商品 -- 注文明細
```

#### Event - Event

```text
注文 -- 出荷
請求 -- 入金
注文 -- 注文明細
契約 -- 契約更新
```

#### Resource - Resource

- 対応表
- 組み合わせ
- 所属
- 分類関係
- 日付や数量などの Event 性を持つ属性が付く場合は、Event として扱えないか検討する。

```text
商品 -- 取引先
社員 -- 部署
商品 -- カテゴリ
```

#### Recursive

- 同一 Entity 内の階層、親子、前後、代替関係。

```text
組織 -- 親組織
商品 -- 代替商品
社員 -- 上司
工程 -- 後続工程
```

### 6. 多値を縦持ちにする

```text
顧客
- 顧客ID
- 電話番号1
- 電話番号2
- 電話番号3
```

```text
顧客
- 顧客ID
- 氏名

顧客連絡先
- 顧客ID
- 連絡先種別
- 電話番号
```

- 電話番号、メールアドレス、住所
- 明細行
- タグ、カテゴリ、資格、権限
- 履歴
- 価格、単価、料率の適用期間
- 状態変更
- 添付ファイル
- コメント、メモ

### 7. Header / Detail を分ける

```text
注文
- 注文ID
- 顧客ID
- 注文日

注文明細
- 注文ID
- 行番号
- 商品ID
- 数量
- 単価
```

- 明細は独立した業務事実として扱う。

### 8. 状態と履歴を分ける

```text
契約(Resource)
- 契約ID
- 現在ステータス

契約状態変更(Event)
- 契約ID
- 変更日時
- 変更前ステータス
- 変更後ステータス
- 変更理由
```

- 現在値だけで十分な項目と、履歴として残すべき項目を分ける。

### 9. 属性を配置する

- その属性はどの Identifier によって一意に決まるか。
- その属性の値はいつ変わるか。
- 過去値を残す必要があるか。
- 集計・監査・再計算で必要になるか。
- Resource の性質か、Event の発生事実か。
- 顧客名は顧客に置く。
- 注文日は注文に置く。
- 注文数量は注文明細に置く。
- 商品の現在価格は商品に置いてもよいが、販売時単価は注文明細に置く。
- 価格改定を追う必要がある場合は商品価格履歴を Event として置く。

### 10. 検証する

- 論理的に無矛盾な `L-真` のモデルになっているか。
- 現実の事業事実と一致した `F-真` のモデルになっているか。
- 全 Entity が Resource または Event に分類されているか。
- Event には発生日、処理日、適用日などの時間軸があるか。
- 数量・金額・単価などの実績値が正しい粒度にあるか。
- 多値属性が横持ちになっていないか。
- 明細、履歴、状態変更が必要に応じて縦持ちになっているか。
- Resource 同士の関係に、実は Event として扱うべき属性が含まれていないか。
- 画面や帳票の都合で作っただけの Entity が混ざっていないか。
- 業務で認知されていない便宜的なIDや区分を追加していないか。
- 主キー、候補キー、外部キーの根拠を説明できるか。
- 業務上の質問にアクセスパスで答えられるか。

## その他ルール

### 業務語を優先する

- 画面、帳票、伝票、規約、ヒアリングで実際に使われている共有語を優先する。
- 分析者や実装者の都合だけで名前、区分、識別子を追加しない。

### 個体指定子を確認する

- 番号、コード、No.、IDなどを確認する。
- 物理DB用のサロゲートキーと、業務で認知された個体指定子を混同しない。

### Resource-Resource は慎重に扱う

- Resource 同士の関係は、対照表や制約束縛を表す。
- 日付、開始、終了、数量、金額、状態変化があるなら、Event として扱うべきか確認する。
- 社員と部署の現在対応だけなら対照表。
- 配属日、異動日、兼務期間を扱うなら配属 Event または配属履歴を検討する。

### 区分を検証する

- 区分は集合を切断するためのものとして扱う。
- 同じ観点で排他的に分かれているかを確認する。
- `個人` / `法人` は顧客種別として同一観点。
- `個人` / `法人` / `重要顧客` は観点が混ざっている可能性が高い。
- 複数の観点が混ざる場合は、サブセット、対照表、別Entityとして分ける。

### 多値をOR/ANDで見る

- `ORの多値`: 役割、分類、区分など、複数の役割や集合の切断に関わるもの。
- `ANDの多値`: 伝票/明細、注文/注文明細のように、複数要素の組み合わせで業務事実を作るもの。
- 横持ちにせず、業務上の意味が説明できる形で縦持ちにする。

## 出力形式

### Entity 一覧

| Entity | 分類 | Identifier | 主な属性 | 備考 |
| --- | --- | --- | --- | --- |
| 顧客 | Resource | 顧客ID | 氏名、顧客区分 | 取引相手 |
| 注文 | Event | 注文ID | 注文日、顧客ID | 顧客が行う注文 |

### Relationship 一覧

| From | To | 種別 | 意味 |
| --- | --- | --- | --- |
| 顧客 | 注文 | Resource-Event | 顧客が注文に関与する |
| 注文 | 注文明細 | Event-Event | 注文が複数明細を持つ |
| 商品 | 注文明細 | Resource-Event | 商品が注文明細に関与する |

### テーブル案

```text
customers
- customer_id PK
- customer_name
- customer_type

orders
- order_id PK
- customer_id FK
- ordered_at

order_lines
- order_id PK/FK
- line_no PK
- product_id FK
- quantity
- unit_price
```

## レビュー時の指摘例

- `電話番号1`, `電話番号2` は多値なので `顧客連絡先` として縦持ちにする。
- `商品` と `顧客` が直接つながっているが、購入・契約・見積などの Event を介すべき。
- `現在ステータス` だけでは履歴が消えるため、状態変更 Event が必要か確認する。
- `単価` が商品マスタにしかないが、販売時単価は注文明細に保存する。
- `部署所属` に開始日・終了日があるため、単なる Resource-Resource ではなく所属履歴 Event として扱う。

## 判断に迷ったとき

- 「これはいつ起きたか」と問えるなら Event 候補。
- 「後から監査・集計・再計算・説明が必要か」と問えるなら Event 候補。
- 「業務上、継続して参照する対象か」と問えるなら Resource 候補。
- 「同じ種類の値が複数あるか」と問えるなら縦持ち候補。
- 「この属性はどの Identifier に従属するか」と問うと配置先を決めやすい。

## 最重要ルール

- Event
- Resource
- 多値 => 縦持ち
- L-真: Logic
- F-真: Fact
